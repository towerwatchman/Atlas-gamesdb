# Deploying to the server

Two separate trees go to two separate places, and they are configured
independently:

| Target | Local | Remote | Then runs |
| --- | --- | --- | --- |
| `python` | repo root | `/home/atlas/svr` | nothing (see below) |
| `node` | `server/admin` | `/var/www/html/admin` | `npm install`, `npm run build`, `pm2 restart atlas` |

These are the live paths, confirmed against the deployed server. If you ever need
to re-derive them:

```bash
pm2 list
pm2 show atlas | grep -i 'exec cwd\|script path'
pm2 show atlas-worker | grep -i 'exec cwd\|script path'
```

**The `python` target should restart the refresh worker.** Its `post_commands` is
empty, but `f95_refresh_worker.py` runs as a long-lived PM2 daemon holding
imported `scraper/` code in memory — a deploy replaces the files on disk and the
worker carries on running the old ones. Add:

```json
"post_commands": ["pm2 restart atlas-worker"]
```

Until then, restart it by hand after any deploy touching `scraper/**` or
`f95_refresh_worker.py`. See [ATLAS_WORKER.md](ATLAS_WORKER.md).

**Check the `node` target's `post_commands` match its `remote`.** Files deploy to
`/var/www/html/admin`, but the post-commands currently `cd /opt/atlas/server/admin`
before `npm install` / `npm run build`. Unless one path is a symlink to the other,
the build runs in the wrong tree and the freshly-uploaded `web/src` is never
compiled into `server/public` — the deploy looks clean and the site serves the old
bundle. Either point the commands at `/var/www/html/admin` or confirm the symlink:

```bash
ls -ld /opt/atlas/server/admin /var/www/html/admin
```

## Configuration

Settings come from three layers, later ones winning:

1. built-in defaults
2. `deploy.json` (next to the exe / at the project root, git-ignored)
3. `.env`, and real environment variables, which beat the `.env` file

### Recommended: put the connection in `.env`

```ini
SFTP_HOST=atlas-gamesdb.com
SFTP_PORT=22
SFTP_USER=deployer
SFTP_PASSWORD=...            # or leave blank and set SFTP_KEY_PATH
SFTP_KEY_PATH=~/.ssh/id_ed25519
SCRAPER_DIR=/opt/atlas-scraper
ADMIN_SERVER_DIR=/opt/atlas/server/admin
```

That is enough on its own — the Deploy tab works with no `deploy.json` present at
all. It also keeps the SFTP password out of a second file: **values supplied by
`.env` are never written into `deploy.json`**, they're blanked on save.

Setting `SFTP_PASSWORD` with no `SFTP_KEY_PATH` selects password auth
automatically. Override with `SFTP_AUTH=key|password` if you need to.

Fields that `.env` controls are shown **read-only** on the Settings tab, labelled
`from .env (SFTP_HOST)`, with a green summary line at the top saying how many
came from where. Editing them in the app would achieve nothing, since `.env` wins
on every load, so the app doesn't pretend otherwise. Change them in `.env` and
press **Reload from .env / disk** — no restart needed.

Anything `.env` doesn't set stays editable in the app and is saved to
`deploy.json` as normal: the include/exclude patterns, local folders,
post-deploy commands, and the two upload options.

> If you edit fields on the Settings tab, press **Save**. The footer with Save
> and Reload is pinned below the scroll area precisely so it can't be missed —
> the field list is far taller than the visible panel.


### deploy.json

Still used for everything `.env` doesn't cover. It sits next to the exe (or at
the project root), is git-ignored, and `deploy/deploy.example.json` is the
committed template.

```jsonc
{
  "connection": {
    "host": "atlas-gamesdb.com",
    "port": 22,
    "user": "root",
    "auth": "key",                          // or "password"
    "key_path": "~/.ssh/id_ed25519"
  },
  "options": {
    "skip_unchanged": true,
    "atomic": true
  },
  "targets": {
    "python": {
      "local": ".",
      "remote": "/opt/atlas-scraper",
      "include": ["api.py", "scraper/**/*.py", "tools/**/*.py", "..."],
      "exclude": ["**/__pycache__/**", "scraper/fixtures/**", "atlas_tools/**"],
      "env_files": [".env"],
      "post_commands": []
    }
  }
}
```

Patterns support `**` properly: `**/` is zero or more path segments, `*` does
*not* cross a `/`. So `**/__pycache__/**` matches at any depth including the top
level, and `web/src/*` is not the same as `web/src/**`.

## What is and isn't uploaded

Deliberately **excluded** from the Python target: `atlas_tools/` (the GUI is a
Windows thing, the server has no use for it), `scraper/fixtures/` (~1.5MB of
saved HTML for tests), `__pycache__`, and `build/`.

Deliberately **excluded** from the Node target: `node_modules/` (installed on
the server) and `server/public/assets/` — those are Vite build output,
regenerated by `npm run build` remotely. Uploading stale local assets is how you
end up serving a frontend that doesn't match the source.

### `.env` files are never uploaded by default

They're listed under `env_files`, separate from `include`, and only go up when
you tick the box on the Deploy tab — which then asks you to type a confirmation
phrase.

This matters because your local `.env` is almost certainly *not* what the server
should have. The server's has `DB_HOST=localhost`, its own `PACKAGE_DIR`
(`/var/www/html/packages`), and production credentials. Overwriting it with a dev
copy points the scraper at the wrong database or breaks packaging outright.

### Nothing is ever deleted remotely

Deleting a file locally leaves the old copy on the server. That's the safe
default, but it means a renamed or removed module needs cleaning up by hand.
The log says so at the end of every run.

## How an upload behaves

- **Unchanged files are skipped** by comparing size and mtime, with 2 seconds of
  slack for filesystem granularity. Local mtime is written to the remote file
  afterwards so the comparison keeps working next time.
- **Uploads are atomic**: written to `<name>.atlastmp`, then `posix_rename`d into
  place, so a running Node process never reads a half-written file.
- **Remote directories are created as needed** (`mkdir -p` equivalent).
- **Post-commands stream their output** into the log and run in order. A non-zero
  exit stops the deploy and raises — but the files are already uploaded at that
  point, nothing is rolled back.

## Recommended sequence

1. Tick only the target you changed.
2. Leave **Dry run** on. Press Deploy. Read the file list.
3. Untick Dry run. Press Deploy. Type `deploy` to confirm.
4. Watch `npm install` / `npm run build` / `pm2 restart atlas` in the log.

For the Python target, restarting the refresh worker isn't automatic. It runs as
a PM2 daemon (`atlas-worker`) with `scraper/` imported into memory, so new
files on disk do nothing until it restarts:

```json
"post_commands": ["pm2 restart atlas-worker"]
```

Confirm the process name with `pm2 list` if it was registered under something
else. Full runbook: [ATLAS_WORKER.md](ATLAS_WORKER.md).

## Host keys

The client loads your known-hosts file and then accepts unknown keys
(`AutoAddPolicy`), which is what makes a first connection work without manual
setup. The trade-off is that a *changed* server key won't hard-fail. The
SHA256 fingerprint is printed on every connect, so it's visible in the log if
you look — worth glancing at the first time so you know what normal looks like.

## Testing the deploy path

`tests/test_deploy_live.py` runs the real thing against an sshd — dry run,
upload, skip-unchanged, single-file change, `.env` gating, and a failing
post-command. Setup instructions are in its docstring. It skips if
`ATLAS_TEST_SSH_HOST` isn't set.

## If paramiko isn't installed

The Deploy tab reports it rather than crashing:

```
pip install -r requirements-desktop.txt
```

The server never needs paramiko; it's only in the desktop requirements.
